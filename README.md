# Task Management API

REST API для керування задачами на FastAPI. Готові структура бази даних, JWT-аутентифікація, CRUD задач, коментарі, пошук і фільтри, статистика та періодичне скасування прострочених задач. Рішення щодо неоднозначних вимог зафіксовані нижче.

## Запуск локально через Docker

Потрібен запущений Docker Desktop із підтримкою Docker Compose.

1. Скопіюй приклад налаштувань і заміни `JWT_SECRET` та `POSTGRES_PASSWORD` у власному `.env`:

   ```bash
   cp .env.example .env
   ```

   `.env` містить секрети й не додається до Git. Значення `DATABASE_URL` у прикладі призначене для запуску Python на комп'ютері; якщо змінюєш пароль або `POSTGRES_PORT`, онови їх і в цьому URL. Для контейнерів Compose автоматично задає адресу бази через ім'я сервісу `db`. Якщо порти зайняті, зміни `POSTGRES_PORT` і `WEB_PORT` у `.env`.

2. Збери й запусти PostgreSQL, міграцію, API та періодичний фоновий процес:

   ```bash
   docker compose up --build --wait
   docker compose ps
   ```

   Параметр `--wait` дочекається готовності сервісів. Очікуваний стан: `healthy` для `db` і `web`, `Exited (0)` для `migrate`, `Up` для `worker`. Сервіс `migrate` автоматично застосовує Alembic-міграції перед запуском API й worker.

3. За потреби міграцію можна повторити вручну — це безпечно, якщо вже застосовано всі ревізії:

   ```bash
   docker compose exec web alembic upgrade head
   ```

   На чистій базі команда створює таблиці `users`, `tasks` і `comments` та записує поточну версію схеми в `alembic_version`.

4. Перевір API:

   ```bash
   curl http://127.0.0.1:8002/health
   ```

   Очікувана відповідь: `{"status":"ok"}`. `/health` також виконує простий запит до PostgreSQL. Документація FastAPI доступна за адресою <http://127.0.0.1:8002/docs>. Якщо порт `8002` зайнятий, зміни `WEB_PORT` у `.env`.

Щоб переглянути журнали або зупинити контейнери:

```bash
docker compose logs web
docker compose down
```

`docker compose down` не видаляє дані PostgreSQL: вони зберігаються у Docker volume `postgres_data`.

## Міграції після додавання моделей

Усі SQLAlchemy-моделі успадковують `Base` із `app/db/base.py`. Нові класи моделей потрібно імпортувати в `app/models/__init__.py`, щоб Alembic бачив їхні таблиці. Після зміни моделей створи нову ревізію, переглянь згенерований файл у `alembic/versions/` і застосуй її:

```bash
docker compose exec web alembic revision --autogenerate -m "describe schema change"
docker compose exec web alembic upgrade head
```

## Архітектура бази й аутентифікації

- `app/models/enums.py` визначає спільні значення статусів (`Backlog`, `In Progress`, `Review`, `Done`, `Cancelled`) і пріоритетів (`High`, `Medium`, `Low`). Моделі SQLAlchemy, Pydantic-схеми й API використовують ті самі enum-класи.
- `app/models/entities.py` описує таблиці: `User` має унікальні логін та email і лише хеш пароля; `Task` містить автора, необов'язкового виконавця, статус, пріоритет і дати; `Comment` належить задачі й автору. Зовнішні ключі та обмеження захищають цілісність даних у PostgreSQL.
- `app/db/session.py` створює асинхронне з'єднання й окремий сеанс для кожного запиту. Сервіс робить `commit` після успішного запису; при помилці сеанс відкочується.
- `alembic/versions/` зберігає версії структури бази. API не викликає `create_all` під час запуску.
- `app/schemas/auth.py` перевіряє запити та визначає безпечні відповіді. `app/services/auth.py` працює з користувачем у базі, а `app/core/security.py` хешує паролі Argon2 і підписує JWT.
- `app/api/auth.py` приймає запити реєстрації та входу. `app/api/deps.py` перевіряє Bearer-токен, його строк дії та наявність користувача в базі; маршрути задач використовують `get_current_user`.
- `app/api/tasks.py` задає маршрути задач і коментарів. `get_current_user` підключений до всього роутера: без валідного токена запити не доходять до операцій із базою. `app/services/tasks.py` перевіряє автора, виконавця, дедлайн, переходи статусів і ліміт активних задач. Той самий сервіс використовує `app/worker.py` для автоматичного скасування прострочених задач.

## Аутентифікація

- `POST /auth/register`: JSON із `username`, `email`, `password`; повертає ID, логін, email і дату створення без пароля чи його хешу. Логін та email не чутливі до регістру.
- `POST /auth/login`: поля форми `username` (можна також вказати email) і `password`; повертає `access_token` та `token_type: bearer`. Строк дії визначається `JWT_ACCESS_TOKEN_MINUTES`, за замовчуванням 60 хвилин.
- `GET /auth/me`: потребує заголовка `Authorization: Bearer <access_token>` і повертає поточного користувача. У `/docs` токен можна ввести кнопкою **Authorize**.

JWT підписаний, але його вміст не зашифрований. У токені є лише ID користувача, час створення і завершення дії; секрет і пароль у нього не записуються.

Приклад отримання токена та авторизованого запиту (у `/docs` можна просто натиснути **Authorize**):

```bash
curl -X POST http://127.0.0.1:8002/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"demo_user","email":"demo@example.com","password":"Strong-Demo-91!"}'

curl -X POST http://127.0.0.1:8002/auth/login \
  -d 'username=demo_user&password=Strong-Demo-91!'
```

Скопіюй `access_token` із другої відповіді та передай його в заголовку `Authorization: Bearer <access_token>`. Наприклад: `curl -H 'Authorization: Bearer <access_token>' http://127.0.0.1:8002/auth/me`.

## Поточні маршрути задач і коментарів

Усі маршрути `/tasks` вимагають `Authorization: Bearer <access_token>`. Автор задачі та коментаря визначається із токена, а не з JSON запиту.

| Метод і шлях | Дія |
| --- | --- |
| `POST /tasks` | Створити задачу. JSON: `title`, `description`, `priority`, необов'язковий `assignee_id`, `deadline` з часовим поясом. |
| `GET /tasks` | Список усіх задач із пошуком, фільтрами, сортуванням і `offset`/`limit` (1–100). За замовчуванням: High → Medium → Low, потім найближчий дедлайн та ID. Відповідь: `items`, `total`, `offset`, `limit`. |
| `GET /tasks/overdue` | Прострочені активні задачі за дедлайном та ID із `offset`/`limit`. |
| `GET /tasks/stats` | Загальна кількість, кількість за кожним статусом і пріоритетом, `overdue_count` та `active_count`. |
| `GET /tasks/{id}` | Прочитати задачу. |
| `PATCH /tasks/{id}` | Автор змінює дозволені поля, крім статусу. |
| `PATCH /tasks/{id}/status` | Автор або виконавець змінює статус через дозволений перехід; вручну скасовує лише автор. |
| `DELETE /tasks/{id}` | Автор видаляє лише `Done` або `Cancelled`. |
| `POST /tasks/{id}/comments` | Авторизований користувач додає коментар. JSON: `text`. |
| `GET /tasks/{id}/comments` | Коментарі конкретної задачі з `offset` і `limit` (1–100), за датою та ID. Відповідь: `items`, `total`, `offset`, `limit`. |

Наприклад, тіло запиту для створення задачі:

```json
{
  "title": "Підготувати демо",
  "description": "Перевірити API",
  "priority": "High",
  "assignee_id": null,
  "deadline": "2030-10-25T15:00:00+03:00"
}
```

Значення `status`, `priority` у відповіді та перевірці запиту походять зі спільних enum-класів. Відповідь задачі містить `author` і `assignee` з ID та логіном, а також їхні ID у полях `author_id` і `assignee_id`. Усі списки та статистика доступні лише з JWT.

Для `GET /tasks` доступні `search` (пошук без урахування регістру в назві й описі), `status`, `priority`, `assignee_id`, `deadline_from`, `deadline_to`, `sort_by` (`priority`, `created_at`, `deadline`) і `sort_order` (`asc`, `desc`). Межі дедлайну включні та вимагають часового поясу. Фільтри можна комбінувати; `total` рахується після фільтрації, до пагінації. Невідоме поле сортування або некоректний діапазон дає відповідь 422. Для однакових значень сортування ID забезпечує стабільний порядок.

Приклад комбінованого запиту: `GET /tasks?search=report&priority=High&assignee_id=4&sort_by=deadline&sort_order=asc&offset=0&limit=20`.

Задача починається в `Backlog`. Дозволені ручні переходи: `Backlog → In Progress`, `In Progress → Review`, `Review → Done`, а також `Backlog → Cancelled` і `In Progress → Cancelled` (скасувати вручну може лише автор). Повернення до попереднього статусу заборонено. Для `Done` потрібні виконавець і дедлайн, що ще не минув. Статуси `Done` та `Cancelled` термінальні; worker може окремо скасувати прострочену активну задачу, у тому числі зі статусом `Review`.

## Тести

Тести використовують окрему PostgreSQL-базу з назвою, що закінчується на `_test`. Створи її один раз, застосуй міграцію та запусти перевірки:

```bash
docker compose exec db sh -c 'createdb -U "$POSTGRES_USER" "${POSTGRES_DB}_test"'
docker compose exec web sh -c 'DATABASE_URL="${DATABASE_URL%/*}/${POSTGRES_DB}_test" alembic upgrade head'
docker compose exec web sh -c 'TEST_DATABASE_URL="${DATABASE_URL%/*}/${POSTGRES_DB}_test" python -m pytest -q'
```

Якщо тестова база вже існує, першу команду повторювати не треба. Звичайні API-тести відкатують свої зміни; тести одночасних дій використовують окремі з'єднання та видаляють створені ними записи після перевірки. Робоча база не змінюється. Тести покривають реєстрацію, JWT, усю таблицю переходів статусів, CRUD, пошук і комбіновані фільтри, статистику, часові межі, конфлікт worker із ручною зміною статусу та повний сценарій від реєстрації до статистики.

## Прийняті рішення щодо правил

- **Todo і Backlog.** `Todo` у вимозі про ліміт активних задач означає `Backlog`. Окремого статусу `Todo` немає. Активні статуси: `Backlog`, `In Progress`, `Review`.
- **Права доступу.** Усі авторизовані користувачі можуть бачити задачі та коментарі й залишати коментарі. Створювати задачі може будь-який авторизований користувач. Редагувати задачу, призначати виконавця та видаляти задачу може тільки її автор. Змінювати статус за дозволеними переходами може автор або призначений виконавець; вручну переводити задачу в `Cancelled` може тільки автор. Неавторизовані користувачі не мають доступу до задач і коментарів.
- **Дедлайн.** Дедлайн — дата й час із часовим поясом. API приймає ISO 8601 зі зміщенням від UTC, наприклад `2026-10-25T15:00:00+03:00`; у базі час зберігається в UTC. Задача прострочена, якщо `deadline < поточний час UTC`. Це саме правило застосовується в API, статистиці, SQL-запитах, фоні й тестах.
- **Видалення.** Видаляти можна лише задачі у статусах `Done` або `Cancelled`. Задачі `Backlog`, `In Progress` і `Review` не видаляються. Заборона редагувати `Done` і `Cancelled` не забороняє їх видалення за цим окремим правилом.
- **Автоматичне скасування.** Періодичний фоновий процес може переводити прострочені незавершені задачі, зокрема `Review`, у `Cancelled`. Це системний перехід; користувач не може виконати його через endpoint зміни статусу, якщо такого переходу немає в дозволеному графі.
- **Статистика й видимість.** Авторизовані користувачі бачать усі задачі системи. Звичайний список, список прострочених і статистика використовують однакову область видимості: усі задачі системи.

## Періодична перевірка

Окремий контейнер `worker` запускає перевірку кожні `WORKER_INTERVAL_SECONDS` секунд (за замовчуванням 60) без HTTP-запиту. Він скасовує прострочені активні задачі в транзакції з блокуванням рядків. Зайняті іншим запитом рядки пропускає і перевіряє знову під час наступного циклу; повторний запуск не змінює вже завершені або скасовані задачі. Журнал: `docker compose logs worker`. Після автоматичного скасування задача зникає зі списку `/tasks/overdue`, тому цей список може бути порожнім, навіть якщо дедлайни вже минали. `BackgroundTasks` FastAPI виконуються лише після HTTP-відповіді й самі по собі не забезпечують повторення.
